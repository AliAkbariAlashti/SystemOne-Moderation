# Integrating an application with the moderation service

This service is designed to be used asynchronously through RabbitMQ. Your application publishes text for moderation and consumes a result later. This keeps user-facing requests fast and lets the moderation system scale independently.

## Integration flow

```text
Your application
  │
  │ publish a persistent moderation request
  ▼
moderation.requests
  │
  ▼
Jev moderation worker
  │
  │ publish a persistent result
  ▼
your-app.moderation.results
  │
  ▼
Your application updates its database record
```

## 1. Create an application-owned result queue

Every integrating application should have a durable queue of its own. Do not make several applications consume the fallback `moderation.results` queue: RabbitMQ distributes messages among competing consumers.

Examples:

```text
social.moderation.results
shop.moderation.results
forum.moderation.results
```

Declare this queue during application startup or through infrastructure-as-code.

## 2. Publish a moderation request

Publish a persistent message to the durable `moderation.requests` queue.

### JSON body

```json
{
  "id": "post_01JXYZ",
  "text": "The text that needs moderation.",
  "type": "noul",
  "metadata": {
    "app": "social",
    "author_id": "user_42",
    "content_type": "post"
  }
}
```

| Field | Required | Meaning |
| --- | --- | --- |
| `id` | Yes | Your stable content or moderation-job identifier. |
| `text` | Yes | The exact text to assess. |
| `type` | Yes | The Jev question type to run: `noul`, `choice`, or `score`. Only configured classes with this type run. |
| `metadata` | No | Context your application retains for traceability. The current policy assesses `text`. |

### AMQP properties

| Property | Required | Value |
| --- | --- | --- |
| `delivery_mode` | Yes | Persistent (`2`). |
| `correlation_id` | Yes | A unique request/job ID generated by your app. |
| `reply_to` | Yes | Your durable result queue, e.g. `social.moderation.results`. |
| `content_type` | Recommended | `application/json`. |

The service copies `correlation_id` to the result, making it safe to match a reply to an application job.

## 3. Consume the result

The response body has this shape:

```json
{
  "id": "post_01JXYZ",
  "action": "review",
  "model": "jev-1.x.x",
  "findings": [
    {
      "class_id": "hate_or_harassment",
      "type": "noul",
      "action": "review",
      "probability": 0.61
    },
    {
      "class_id": "severity",
      "type": "score",
      "action": "review",
      "score": 1.4,
      "confidence": 0.82
    }
  ]
}
```

Use the final `action` for product behavior:

| Action | Recommended application behavior |
| --- | --- |
| `allow` | Mark content published/visible. |
| `review` | Mark content pending and send it to human moderation. |
| `block` | Keep content hidden and show the user an appropriate rejection. |

The `findings` are useful for a moderator UI, audit records, analytics, and explanations. They should not replace the final `action` in normal product routing.

## Recommended database lifecycle

Create content as pending, rather than displaying it before moderation completes:

```text
draft → pending_moderation → published
                           → awaiting_human_review
                           → blocked
```

Make the result consumer idempotent. A safe approach is to store `correlation_id` or the content ID with a unique constraint, then ignore an already-applied result.

## Node.js example (`amqplib`)

```js
import amqp from "amqplib";

const connection = await amqp.connect(process.env.AMQP_URL);
const channel = await connection.createChannel();
const resultQueue = "social.moderation.results";

await channel.assertQueue("moderation.requests", { durable: true });
await channel.assertQueue(resultQueue, { durable: true });

const content = {
  id: "post_01JXYZ",
  text: "The text that needs moderation.",
  type: "noul",
  metadata: { app: "social", author_id: "user_42", content_type: "post" }
};
const correlationId = crypto.randomUUID();

channel.sendToQueue(
  "moderation.requests",
  Buffer.from(JSON.stringify(content)),
  {
    persistent: true,
    contentType: "application/json",
    correlationId,
    replyTo: resultQueue
  }
);

channel.consume(resultQueue, async (message) => {
  if (!message) return;
  const result = JSON.parse(message.content.toString());

  // Update the row for result.id. Make this operation idempotent.
  // result.action is: allow, review, or block.
  console.log(message.properties.correlationId, result);
  channel.ack(message);
});
```

## Go example (`amqp091-go`)

```go
channel, err := connection.Channel()
if err != nil { panic(err) }

resultQueue := "shop.moderation.results"
_, _ = channel.QueueDeclare("moderation.requests", true, false, false, false, nil)
_, _ = channel.QueueDeclare(resultQueue, true, false, false, false, nil)

request := []byte(`{"id":"listing_123","text":"Item description","type":"noul"}`)
correlationID := uuid.NewString()

err = channel.PublishWithContext(ctx, "", "moderation.requests", false, false,
  amqp.Publishing{
    ContentType: "application/json",
    DeliveryMode: amqp.Persistent,
    CorrelationId: correlationID,
    ReplyTo: resultQueue,
    Body: request,
  },
)
if err != nil { panic(err) }

deliveries, _ := channel.Consume(resultQueue, "shop-app", false, false, false, false, nil)
for delivery := range deliveries {
  // Decode delivery.Body, atomically update the matching listing, then ack.
  delivery.Ack(false)
}
```

## Python example (`pika`)

Install the RabbitMQ client:

```sh
pip install pika
```

```python
import json
import os
import uuid

import pika

connection = pika.BlockingConnection(
    pika.URLParameters(os.environ["AMQP_URL"])
)
channel = connection.channel()
result_queue = "forum.moderation.results"

channel.queue_declare(queue="moderation.requests", durable=True)
channel.queue_declare(queue=result_queue, durable=True)

content = {
    "id": "comment_123",
    "text": "The text that needs moderation.",
    "type": "noul",
    "metadata": {
        "app": "forum",
        "author_id": "user_42",
        "content_type": "comment",
    },
}
correlation_id = str(uuid.uuid4())

channel.basic_publish(
    exchange="",
    routing_key="moderation.requests",
    body=json.dumps(content).encode(),
    properties=pika.BasicProperties(
        content_type="application/json",
        delivery_mode=pika.DeliveryMode.Persistent,
        correlation_id=correlation_id,
        reply_to=result_queue,
    ),
)


def handle_result(channel, method, properties, body):
    result = json.loads(body)
    # Atomically update the row for result["id"]. Make this idempotent.
    # result["action"] is "allow", "review", or "block".
    print(properties.correlation_id, result)
    channel.basic_ack(delivery_tag=method.delivery_tag)


channel.basic_consume(
    queue=result_queue,
    on_message_callback=handle_result,
    auto_ack=False,
)
channel.start_consuming()
```

## Reliability requirements

- Use durable queues and persistent messages.
- Use publisher confirms in production, so a producer knows RabbitMQ accepted a request.
- Acknowledge a result only after its database update succeeds.
- Make both publishing and consuming idempotent; broker redelivery is normal.
- Monitor queue depth, redelivery count, consumer lag, and items remaining in `pending_moderation`.
- Add a dead-letter queue policy for messages that repeatedly fail due to malformed payloads or application errors.

## HTTP endpoint

`POST /v1/moderate` remains available for health/debug tools or a genuinely synchronous product path. For ordinary application content, prefer RabbitMQ.
